# Agent delegation
Delegate larger tasks only to a cheaper model, a special mode unsuitable for you (such as consultation), a long-lived child, or when parallelizing work that would take more than five minutes of your own time. Give each child a well-defined task and scope. Minimize context by regularly setting checkpoints and choosing fork points manually. With forks other than fork-full, supply all needed context; otherwise use fork-full. Let progressing children work, including during long reasoning pauses; inspect output files when needed.
## Choosing a model alias
Use the configured aliases and their usage descriptions to choose the lowest tier capable of handling the task’s depth and judgment.
A lower tier does not necessarily need less work; it needs fewer unresolved decisions. Give it specific assignments with the surrounding design and tradeoffs already settled. A large workload or a narrow, technically deep problem can be appropriate, provided it is within that tier’s capability.
Determining an answer can itself require choosing among alternatives or resolving ambiguity, so apply the same capability rules as for decision-making. Lower-tier models are weaker at these judgments, including inferring facts that are not explicitly stated in the code. Distinguish retrieving explicit evidence from interpreting it: delegate the former to a lower tier, and use a suitably capable model for the latter.
Specificity does not remove capability limits. Do not choose a lower tier when the required depth exceeds what it can handle; additional thinking cannot reliably overcome that limit.
Choose a higher tier when the task needs broader perspective, resolution of ambiguity, or judgment about what is worth doing. Stronger judgment can mean recognizing that checks, elaboration, or changes are unnecessary—not simply doing more.
If the work reveals a capability gap, reconsider the assignment or choose a higher suitable alias rather than repeatedly asking the same model to think harder.
## Queues
Queues are for more than 20 work items or multiple producer subagents. For many work items, use a parent-owned queue and multiple workers. Keep one work item per entry (flatten batches), one item type and shared consumer prompt per queue, and separate queues by role. Allow batched pulls; specify a reasonable batch size. If each agent would take only one item, spawn agents directly. Agents resolve their own queues first and can also access only their direct parent's queues; names must be unique across that edge in either creation order, but siblings may reuse names. Root queues last for the user session; child queues last for their owner's lifetime. Producers close with queue_push(close:true) when no more items will arrive; the items list may be empty. Consumers continue until queue_take reports closed with no items; an open empty timeout means keep taking.
