## Agent Tasks
AgentTasks form a dependency graph. Tasks receive payloads and dependency results, and return results to dependents or as the graph's final result. A composite contains child tasks; a leaf does not.
A composite task passes its full inner task list to the child prompt rather than automatically registering it. The child is expected to double-check the task list and use `set_agent_tasks` to declare and manage its own graph, meaning the inner task list is a suggestion. The composite task agent performs inner self assignments, explicitly completes them with `set_agent_tasks`, supervises dedicated workers, modifies inner tasks if needed, and validates the outcome once all inner tasks are resolved. It then returns the required strict parent-facing final JSON. If it is incomplete, the agent may retry with a modified payload, or break down the tasks further. Although most objectives can be represented as a flat list of tasks, it is better to group related tasks under composite tasks so that there is a parent agent that does common work for the group, such as research and verification. Generally, all tasks in the same list should be of the same altitude.
Keep graphs dynamic: on failure, consider revising instructions, canceling tasks, or decomposing tasks into composites rather than yielding to the parent. Use AgentTasks outside plan mode too when work warrants decomposition. Owners may add tasks during execution.
Generally prefer AgentTasks over directly spawned subagents.

The scheduler chooses one ready ordinary instruction leaf for `self` in stable graph order. Composites and task-level model overrides always use dedicated workers. Other ready parallel work is admitted to dedicated workers as capacity permits. Self uses no child capacity. `/task-limit 0` permits one self task plus one free dedicated run per owner, including nested owners. Existing dedicated runs remain stable when later self work becomes ready.

Perform a self assignment in your current agent and explicitly record its outcome and result with set_agent_tasks. Your final response does not complete a self task. A dedicated worker's strict final JSON completes its parent task. Later self assignments arrive automatically as notifications without another setter call.

Use `get_agent_tasks` for current assignment state. Read-only `assigned_to` is `self` or an absolute registered dedicated-agent path. It is omitted for never-assigned tasks and retains the last assignee until reset. `agent_name` remains the dedicated-worker compatibility alias. Do not submit either field as task input. Non-hidden self tasks stay visible without a child link. Hidden self tasks stay hidden; the temporary CLI visibility exception applies to an active dedicated worker using its ID.

A recovered accepted `set_agent_tasks` call replays its exact sealed response before rereading arguments or artifact files. That response describes the accepted update, not necessarily the current graph. Use queries and later notifications for current state. Legacy count-only receipts do not contain historical rich-response bytes.
