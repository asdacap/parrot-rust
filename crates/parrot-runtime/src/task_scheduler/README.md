# Retained task scheduler (T50)

AI-generated by Parrot, GPT-6.1-sol/high (`medium_llm`). Ported from pinned

## Composition

Each actual T48 `Scope<S>` owns one `TaskScheduler<S, P>`. `P` implements the
existing domain `TaskArtifactParser`; runtime never depends on the tools parser
implementation and does not parse task JSON itself. Construct `TaskSessionAdapter`
with a **clone of the very same T46 `AgentSession<B>`** used by T48's
`SessionAdapter`. Register the exact `Arc<dyn TaskSession>` as
`ServiceRegistration::new::<dyn TaskSession>(session.clone())` and the exact
scheduler Arc as `ServiceRegistration::new(scheduler.clone())`.

`SchedulerConfig` carries the prepared identity/history, weak actual registry,
that session adapter, actual template catalog/output-blob store, model router,
publisher, diagnostics and lifetime. A new task's selection and fork boundary are
captured once. Completed-history boundaries become safe-prefix boundaries. On
first spawn only, the scheduler locates the registered owner by **Arc identity**
in its weak registry, checks the exact registered scheduler/session services, and
uses the actual owner's `get_or_spawn`. Missing/mismatched registration fails
clearly; there is no name/ID fallback or shadow scope/registry. The launch callback
is lazy, so a preexisting manual worker retains its selection/delivery and does
not resolve a new model override. Each entry retains its actual child scope.

Add `scheduler.work_owner()` to the scope's owned-work entries. Its `OwnedWork`
adapter immediately reserves the owned settlement operation when `settle` is
called, before returning the observation future. Scope disposal can then join it before session,
child and shared-resource disposal. There is no strong owner-scope back reference
or binding hook, so arbitrary nested scopes use the same construction pattern.

## Ownership and observations

- `set_tasks` synchronously admits and reserves a FIFO update, returning an
  already-started `children::Operation<()>`. Dropping an observer does not drop
  the admitted update, append/publication, spawn or execution. Join it to observe
  validation/publication errors. Consecutive calls preserve admission order even
  when neither handle is awaited.
- `apply_visibility_changes` is also admitted FIFO. After settlement admission it
  is a no-op, matching the source. `settle` synchronously rejects subsequent task
  updates and returns the same retained operation on repeated calls.
- `snapshot` and `capture_detail` are asynchronous, first joining previously
  admitted updates and then taking the same graph gate. Spawn and durable
  publication hold this gate; there is no externally observable intermediate
  Pending state during asynchronous construction. Reads do not wait for ongoing
  settlement executions: they can inspect the graph's canceled state while
  cleanup joins, as the source permits.
- Runner completion uses the graph gate after joining the entry's complete prior
  execution, including forced-stop recording. It reads the latest task at that
  point. Its first poll runs under that gate, preserving the source's synchronous
  prompt/session-enqueue prefix; the retained pending future is then awaited
  **without** the gate across the turn. Completion merges only state/result/
  failure, preserving live visibility. A canceled/restarted run cannot overwrite
  its replacement.
- Settlement cancels unresolved tasks, appends/publishes the final graph, cancels
  runs, joins all admitted executions/stop records, then drains the notifier.
  Publication/spill failures remain observable operation errors; source-caught
  stop-record/final-delivery failures emit bounded typed diagnostics instead.
  Before each start, **all** finished execution handles are joined and pruned.
  Only one first execution error is retained for settlement; later errors emit
  bounded diagnostics immediately, not an ever-growing collection of failed
  handles. Unfinished operations remain owned, and each entry keeps only its
  latest `LastExecution` barrier. Both successful and failed restarts are bounded.

### Two approved ownership corrections, not source-equal failure timing

1. **Stop-record lifetime:** source `AgentTaskService.Execute` removes its
   execution from `_executions` under the gate **before** awaiting `RecordStop`
   (lines 347–353), so concurrent settlement can miss that final record. Here the
   operation finishes only **after** the stop record, and pruning keeps every
   unfinished operation. This preserves the required restart/settlement join
   obligation; it introduces no new task-state transition.
2. **Failure-resilient settlement:** source `SettleCore` (lines 146–177) stops
   cleanup when shutdown-template rendering/final publication fails, or when
   `Task.WhenAll(executions)` fails before notifier settlement. Under the explicit
   consolidated T50/P06 authorization, Rust instead continues cancellation and
   joins **every** owned execution/stop record and the notifier even after those
   failures, fulfilling the frozen `OwnedWork` lifetime contract. These failure
   branches intentionally are not claimed source-equal.

Settlement returns the deterministic first error in phase order: shutdown Render/
final Publish, the prior execution-error summary, remaining executions in start
order, then notifier. Each later error remains observable through bounded typed
`TaskDiagnostic` fields: `operation` is `settlement_publish`, `execution`, or
`settlement_notifier`; `outcome` is `failed`, and `error_code` uses the existing
allowlist. No prompt, exception body, task/model name or policy data is copied
into these diagnostics. Successful cleanup emits no failure diagnostic.

The graph is in memory, as in the source: protobuf progress snapshots are durable
history events (append **before** committed publication), not a new graph
repository or invented rehydration algorithm. Failed tasks hold dependents;
cancellation is an effective transitive state rather than a permanent rewrite of
pending declarations. Successful resets invalidate transitive running/succeeded/
failed dependents. Auto-hide occurs only on a nonempty false-to-resolved edge
(all effective states succeeded/canceled), permitting explicit unhide until the
next edge. Nested payloads are prompt data; parent updates never register or
synchronize a child's independent graph.

## Runner and notifications

Defaults come from `predefined_config.agent_tasks.yaml`: five attempts, three
response repairs per attempt, dependency-first fork history. A rejection can
replace an instruction only (never a composite), carry a replacement result, and
append feedback. Repair attempts do not consume verdict attempts. The runner uses
real `agent-task.*` template IDs. Context/summary bounds are 16 Ki UTF-16 units;
prompt header budget is 256 Ki UTF-16 units minus suffix length. The truncation
notice itself is outside the budget; an already-oversized suffix remains whole.
Composite serialization preserves source field ordering, optional omission,
lowercase states and default JavaScriptEncoder-style escapes.

The notifier starts on first enqueue and consumes one ordered channel. Oversized
text uses the existing T47/storage output-blob primitive once before delivery.
Each notice has one message ID across three attempts with one-second retry
intervals. Wake notices send/steer normally; once notifier settlement begins,
remaining notices record without waking. No timing abstraction or new dependency
is introduced. Diagnostics contain bounded operation/outcome/error-code values
and opaque identifiers, never task/model/prompt/failure bodies.
